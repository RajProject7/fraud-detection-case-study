1. The problem: fraud is rare

Most payments are safe. Only 3.5 in every 100 are fraud. This makes the task hard.

All 590,540 payments

Safe: 569,877 (96.5%)Fraud: 20,663 (3.5%)

Think about a model that says "safe" for every payment. It is correct 96.5% of the time. It finds zero fraud. So accuracy is a bad measure here. I do not report it anywhere in this project.

I use three measures instead:

  • Precision. Of the payments the model flags, how many are really fraud?
  • Recall. Of all the fraud, how much does the model find?
  • PR-AUC. How well the model ranks fraud above safe payments. It ignores the large number of safe payments, so it is a fair score for rare events.

3. How I built it

The pipeline has six steps. The order of steps 2 and 3 matters most.

  1. 1
    Explore the dataClass balance, missing values, amounts, product types.
  2. 2
    Split first: 80% train, 20% testThe split keeps the same fraud share in both parts. The test set stays untouched until the end.
  3. 3
    Build features from the training part onlyAny counts or encodings come from training data. If test data leaks in, the scores look better than they are.
  4. 4
    Train two modelsThe same XGBoost settings. One uses the raw data. One uses SMOTE (explained below).
  5. 5
    Score both on the same unseen test set118,108 real payments, 3.5% fraud.
  6. 6
    Serve the better model with FastAPIOne endpoint, /predict, scores one payment.

I made these features, each from a finding in step 1:

  • Log of the amount. Amounts have a long tail of big purchases. The log makes the spread easier for the model to use.
  • Hour and day of week. Fraud scripts often run at night.
  • Device data present. From the finding above.
  • Email domains match. A buyer and a recipient with different email domains can be a warning sign.
  • How common is this card. A card the model rarely sees is a different risk from a card it sees often.
  • Count of missing fields. It shows which system produced the row.

4. Results

The model flags few payments, and most of its flags are right. It misses about half of the fraud.

Precision: 0.93

Take 100 flagged payments. About 93 are fraud. About 7 are safe payments flagged by mistake.

Recall: 0.50

Take 100 fraud cases. The model finds about 50. The other 50 get through.

Recall is the weak point. I use the standard 0.5 cut-off. A lower cut-off would find more fraud but flag more safe payments. The right cut-off depends on what a miss costs against what a false alarm costs. I do not have those costs, so I did not tune it.

The surprise. SMOTE makes fake fraud examples so the training data is balanced. Many guides say it helps. Here it made every score worse. I report this result and I ship the plain model. I did not want to pick the method I expected to win.

5. Where it is weak

This is a portfolio project. It is not a production fraud system.

  • Random split. The data is ordered in time, but I split it at random. A real system only knows the past. A time-based split would give a lower, more honest score.
  • No tuning. I used fixed, sensible settings for both models. This keeps the comparison fair. It also means the scores are not the best this data can give.
  • The API sees less than the test did. The test used 435 features. The /predict endpoint takes only 16 plain payment fields, such as amount, product type, card type and email domains. The rest are missing, so live scores are less accurate than the table above.
  • Left out on purpose. Free-text device and browser strings. Parsing them well is a project of its own.

6. What I would do next

  • Switch to a time-based split and report the new scores.
  • Choose the cut-off from a real cost for missed fraud and for false alarms.
  • Parse the device and browser strings into usable features.
  • Add a monitoring check for drift, because fraud patterns change.
