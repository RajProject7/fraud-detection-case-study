The problem: fraud is rare

Most payments are safe. Only 3.5 in every 100 are fraud. This makes the task hard.

All 590,540 payments

Safe: 569,877 (96.5%)Fraud: 20,663 (3.5%)

Think about a model that says "safe" for every payment. It is correct 96.5% of the time. It finds zero fraud. So accuracy is a bad measure here. I do not report it anywhere in this project.

I use three measures instead:

Precision

Of the payments the model flags, how many are really fraud?

Recall

Of all the fraud, how much does the model find?

PR-AUC

How well the model ranks fraud above safe payments. It ignores the large number of safe payments, so it is a fair score for rare events.

How I built it

The pipeline has six steps. The order of steps 2 and 3 matters most. The highlighted steps stop test data from leaking into training.

  1. STEP 1Explore the dataClass balance, missing values, amounts, product types.
  2. STEP 2Leak guardSplit first: 80% train, 20% testThe split keeps the same fraud share in both parts. The test set stays untouched until the end.
  3. STEP 3Leak guardBuild features from the training part onlyCounts and encodings come from training data. If test data leaks in, the scores look better than they are.
  4. STEP 4Train two modelsThe same XGBoost settings. One uses the raw data. One uses SMOTE, which makes extra fake fraud examples.
  5. STEP 5Score both on the same unseen test set118,108 real payments, 3.5% fraud.
  6. STEP 6Serve the better model with FastAPIOne endpoint, /predict, scores one payment.

I made these features. Each one comes from a finding in step 1.

  • Log of the amountAmounts have a long tail of big purchases. The log makes the spread easier to use.
  • Hour and day of weekFraud scripts often run at night.
  • Device data presentFrom the finding in section 2.
  • Email domains matchA buyer and a recipient with different domains can be a warning sign.
  • How common is this cardA card the model rarely sees is a different risk from a card it sees often.
  • Count of missing fieldsIt shows which system produced the row.

Results

The model flags few payments, and most of its flags are right. It misses about half of the fraud.

Recall 0.50

FoundMissed

Take 100 fraud cases. The model finds about 50. The other 50 get through.

Recall is the weak point. I use the standard 0.5 cut-off. A lower cut-off would find more fraud but flag more safe payments. The right cut-off depends on what a miss costs against what a false alarm costs. I do not have those costs, so I did not tune it.

5

Where it is weak

This is a portfolio project. It is not a production fraud system.

Random split

The data is ordered in time, but I split it at random. A real system only knows the past. A time-based split would give a lower, more honest score.

No tuning

I used fixed, sensible settings for both models. This keeps the comparison fair. It also means the scores are not the best this data can give.

The API sees less than the test did

The test used 435 features. The /predict endpoint takes only 16 plain payment fields, such as amount, product type, card type and email domains. Live scores are less accurate than the results above.

Left out on purpose

Free-text device and browser strings. Parsing them well is a project of its own.

6

What I would do next

  • Switch to a time-based split and report the new scores.
  • Choose the cut-off from a real cost for missed fraud and for false alarms.
  • Parse the device and browser strings into usable features.
  • Add a monitoring check for drift, because fraud patterns change.
